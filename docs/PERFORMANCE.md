Run with `performance/run-jmeter.sh` (Docker image) or a local JMeter: `jmeter -n -t performance/jmeter/apg-load.jmx -l out.jtl -e -o report -Jthreads=20 -Jduration=60 -Jcreds=performance/data/credentials.csv`.

## Method
Developer laptop (Windows, all 12 JVMs + Postgres + Kafka + Redis + the load tool on the same machine), 20 connections, 20 s per scenario, one merchant, ~15 000 orders in the table by the end. Treat the numbers as relative, not as capacity of the target environment (OCI sizing needs a repeat on real hardware).

## Findings and fixes
| Finding (how it was seen) | Fix | Guard |
|---|---|---|
| `GET /orders` and `/payments` page of 20 cost ~42 and ~22 SQL statements (N+1; service-direct 63 rps) | batch-load customers/items/intents per page | statement-count tests in OrderFlowTest / PaymentFlowTest (<= 5 / <= 4 statements) |
| API-key verification = extra hop + 2 DB reads on every call (gateway path 3x slower than calling order-service directly: 106 vs 292 rps) | gateway caches positive verifications 5 s (SHA-256 key, never invalid keys), user->merchant 30 s | GatewayFlowTest (one hop for repeated calls, re-verified after TTL, bad keys never cached) |
| Test isolation: outbox test shared a table | `@BeforeEach` cleanup | - |

Revocation trade-off: a revoked or suspended API key keeps working for at most `apg.gateway.api-key-cache-ttl` (5 s; `0s` disables the cache).

## Results (same machine, same data)
| Scenario | before: rps / p50 / p95 | after: rps / p50 / p95 / p99 |
|---|---|---|
| create order | 74 / 183 / 1329 ms | **165 / 92 / 250 / 311 ms** |
| create order + payment (2 calls) | 30 / 408 / 4352 ms | **137 / 143 / 418 / 478 ms** |
| list orders | 50 / 340 / 1242 ms | **267 / 66 / 155 / 198 ms** |
| list payments | 58 / 299 / 902 ms | **291 / 63 / 119 / 152 ms** |
| forged PayU callback (rejected) | 253 / 68 / 160 ms | 284 / 59 / 148 / 177 ms |
| ledger balance with JWT | 325 / 27 ms | **670 / 12 ms** |
All requests succeeded (0 errors, 0 unexpected statuses); afterwards `apg_outbox_unpublished`, webhook backlog and DLQ stayed at 0 (the event pipeline kept up with ~14 000 events).
Login is deliberately slow (bcrypt cost 12: ~0.3 s on a quiet machine, ~2 s on the loaded laptop): protect it with the rate limit, do not "optimise" it.

## Next tuning candidates (measure first)
- Remaining per-request overhead is gateway JWT/key handling + one proxy hop + Hibernate; compare with order-service direct (292 rps create, 345 rps list) after the fixes above.
- Connection pools (Hikari 5 locally; size from `max_connections / services`), Tomcat threads, Kafka partitions (3) and consumer concurrency, `count(*)` for page totals on very large tables (consider keyset pagination), Redis rate-limit key per merchant/API key instead of per client address.
- Re-run on OCI hardware, with JMeter, longer soak (>= 30 min) and watch GC/heap, `apg_outbox_oldest_unpublished_seconds`, Kafka lag and DB connections.
