Heading 1: 1. Product Definition
Heading 2: 1.1 Goal
APG is a merchant-facing payment orchestration platform. Merchants create orders and payment requests through APG APIs. APG authenticates the merchant, creates and tracks payment attempts, routes the attempt to an authorized payment provider, verifies the provider result, receives and verifies webhooks, maintains an auditable ledger, handles refunds, settlement records and reconciliation, and exposes operational visibility.
Heading 2: 1.2 What APG is not
APG is not itself a UPI network, card network, bank or acquiring institution.
APG must not pretend to directly authorize cards or UPI unless an authorized processing/acquiring integration actually exists.
Production payment acceptance requires provider onboarding, merchant/KYC/compliance approval and applicable security/regulatory requirements.
Heading 2: 1.3 Core user types
Role | Responsibilities
Merchant Admin | Create/manage merchant account, API keys, webhooks, users and configuration.
Merchant Developer | Create orders/payments, receive webhooks, query status and refunds.
APG Operations | Monitor payments, provider health, reconciliation exceptions and incidents.
APG Finance | Review ledger, settlements, fees and reconciliation.
System Admin | Manage platform configuration and security controls.

Heading 2: 6.2 Idempotency
All money-changing POST operations must support Idempotency-Key. The server stores the request fingerprint and final response or an in-progress marker. A repeated key with the same fingerprint returns the original result. A repeated key with a different request body is rejected.
Heading 2: 6.3 API response conventions

  "data": {...},
  "error": null,
  "requestId": "req_...",
  "timestamp": "2026-..."
}
Error responses must contain a stable machine-readable code, human-readable message, requestId and validation details when applicable.
Heading 1: 7. Payment State Machine
CREATED
  -> PENDING
  -> PROCESSING
  -> AUTHORIZED
  -> CAPTURED
  -> SUCCESS

Failure branches:
PENDING/PROCESSING -> FAILED
AUTHORIZED -> FAILED only where provider semantics allow
SUCCESS -> REFUND_PENDING -> REFUNDED / PARTIALLY_REFUNDED

Unknown provider outcome:
PROCESSING/UNKNOWN -> VERIFY_REQUIRED
VERIFY_REQUIRED -> SUCCESS / FAILED / UNKNOWN (manual or scheduled resolution)
State transitions must be validated centrally.
Every transition creates a state-history record.
Provider callback must not be trusted blindly; verify signature and, where necessary, query provider status.
Timeout does not automatically mean payment failed.

Heading 1: 14. Double-Entry Ledger
The ledger is an accounting subsystem, not a payment status table. Every financial transaction must balance.
Example conceptual capture:
Debit  : Merchant Receivable / Provider Receivable
Credit : Merchant Payable

Example fee:
Debit  : Merchant Payable
Credit : APG Fee Revenue

Example refund:
Debit  : Refund / Reversal account
Credit : Merchant Payable / Provider Receivable
Use immutable ledger transactions and entries.
Store currency and minor-unit amounts.
Require total debit == total credit per transaction.
Use compensating transactions for corrections.
Reconciliation must be possible from ledger plus provider data.
Heading 1: 15. Settlement
Represent provider settlement batches.
Map settlement items to APG payments/ledger transactions.
Calculate gross, fees, refunds, adjustments and net settlement.
Track settlement status and dates.
Never mark settlement successful without provider evidence.
Persist unmatched items as reconciliation exceptions.
Heading 1: 16. Reconciliation
Provider records
      ↓
Normalize
      ↓
Match by provider reference / merchant reference / amount / date
      ↓
Matched ───────────────→ reconciled
      │
      ├─ amount mismatch → exception
      ├─ missing APG     → exception
      ├─ missing provider→ exception
      └─ status mismatch → exception

Reconciliation must be rerunnable.
Do not modify historical evidence to hide a mismatch.
Exceptions need status, owner, reason, evidence and resolution notes.
