# payment-link-service (port 8092, DB `apg_paymentlink`)
Shareable payment links (Razorpay-style "Payment Links"). A merchant creates a link (amount, description, expiry, one-time or reusable); the customer opens `<public-base-url>/pay/<code>` (no login), sees the merchant name and amount on APG's own page and presses Pay, which creates a normal order + payment + hosted checkout on the merchant's behalf and redirects to the provider.
- Merchant API (API key or dashboard user; create/cancel = MERCHANT_ADMIN): `POST /api/v1/payment-links` (Idempotency-Key), `GET /api/v1/payment-links[?status]`, `GET /{id}`, `POST /{id}/cancel`. Response carries `url`.
- Public (no auth, through the gateway): `GET /pay/{code}` page (404 unknown, 410 paid/expired/cancelled), `POST /pay/{code}/start` -> 303 to the checkout. The 10-character unambiguous random code is the only credential and only allows paying that fixed amount; amount, currency and merchant always come from the stored link. Merchant-provided text is HTML-escaped; the page sets its own CSP with a nonce and runs no script.
- One-time links: never two payments in flight (advisory lock + attempt rows; a customer who never reached the provider may retry; one who is at the provider blocks others), PAID only after payment-service confirms (consumes `payment.success` + lazy status check on page open, so a lost event cannot leave a paid link open). Reusable links count every successful payment and stay ACTIVE until expiry.
- Not built: QR codes, SMS/email sending, partial payments, custom fields, link-level webhooks (merchants already get `payment.success` for the payment).
Env: POSTGRES_USER/PASSWORD, INTERNAL_SERVICE_TOKEN, `*_SERVICE_URI` peers, PUBLIC_BASE_URL (host customers use), KAFKA_BOOTSTRAP_SERVERS, APG_EVENTS_ENABLED.
