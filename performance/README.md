# Performance tests (M14)

JMeter plan `jmeter/apg-load.jmx` (generated by `jmeter/generate_plan.py`) drives the gateway at `http://localhost:8080`.

## Safety first
- **Never point this at PayU or at a stack that talks to real PayU.** The plan contains no checkout/verify steps, and `scripts/perf-start.sh`
  starts the stack with the orchestrator verification worker OFF, so synthetic payments can never trigger `verify_payment` calls.
- Forged-callback traffic only exercises the hash-rejection path (no PayU call).
- Run only against a local/disposable environment: the plan creates thousands of orders and payments.

## Run
1. `docker compose up -d` (Postgres/Redis/Kafka), then `bash scripts/perf-start.sh` (stack with a relaxed gateway rate limit).
2. `bash performance/setup-data.sh` creates a merchant + API key + dashboard user and writes `performance/data/credentials.csv` (git-ignored).
3. `bash performance/run-jmeter.sh [threads] [duration-seconds]` (Docker image of JMeter; no local install needed). Results: `performance/results/<timestamp>/` (`results.jtl`, HTML report in `report/`).
Pass/fail guide (initial targets, tune with real hardware): error rate < 0.1% for the write/read scenarios (expected 400 for forged callbacks, 429 not expected with the relaxed limit), p95 < 500 ms for orders/payments at the tested concurrency, no growth of `apg_outbox_oldest_unpublished_seconds` / webhook / DLQ gauges (watch Grafana).
